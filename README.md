# Structural layout grid from a first-floor plan

Given an architect's first-floor plan (vector PDF), this program computes the
building **boundary**, proposes **column** positions, and connects them with
**beams** — the plan-view structural skeleton, as described in
[`ASSIGNMENT.md`](ASSIGNMENT.md).

Run against all three unseen test plans, it self-checks its own boundary area
against the number printed on each sheet:

| CRN | Columns | Beams | Computed area | Stated area | Match |
|---|---|---|---|---|---|
| CRN574114 | 20 | 21 | 690.8 SF | 649 SF | 106.4% |
| CRN642050 | 13 | 14 | 815.1 SF | 744 SF | 109.6% |
| CRN716485 | 17 | 17 | 904.9 SF | 987 SF | 91.7% |

Nothing in the code branches on a CRN — the same five functions run on all
three plans (and on plans the code has never seen) with no hardcoded numbers.

## How to run it

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# one plan
python3 src/pipeline.py test-plans/CRN574114/first_floor_plan.pdf CRN574114 output/CRN574114

# all three test plans at once
python3 src/pipeline.py --all test-plans output

# tests
python3 -m pytest
```

Each CRN's output directory gets `layout.html` (open it in a browser — the
architect's plan next to the computed boundary/columns/beams) and
`layout.json` (the same geometry as data). `output/` in this repo already
has all three, generated by the command above.

**Dependencies:** Python 3.10+, [PyMuPDF](https://pymupdf.readthedocs.io/)
(`pymupdf`) for PDF geometry/text extraction, [Shapely](https://shapely.readthedocs.io/)
for all polygon operations, `pytest` for the test suite. That's the whole
list — see `requirements.txt`.

## Where AI was used

Claude (Sonnet) was used throughout, in an interactive back-and-forth: writing
first drafts of extraction/geometry code, and — more usefully — as a fast way
to dump PDF vector data and iterate on *why* an approach was failing (e.g.
diagnosing that walls are drawn as filled polygons rather than stroked line
pairs; diagnosing why an early boundary algorithm produced a ~500-vertex
maze covering a third of the true area). Every function was read and is
explained below well enough to defend in a walkthrough; nothing was accepted
without checking it against the actual PDF geometry or a rendered overlay.

## What "boundary" means here

**The boundary is the outer face of the exterior walls**, at this floor
level, including a balcony wherever it's enclosed by wall material that
survives Stage 1's gap-closing. Concretely: a wall in these drawings is a
*filled* black polygon (a PDF fill path), while the plot/setback line,
dimension chains, grid lines, hatching and title block are all *stroked*
paths. Stage 0 only ever collects filled polygons into `wall_union_ft`, so
the plot line and page furniture are structurally incapable of leaking into
the boundary — not because of a rule that excludes them, but because they
were never candidate material to begin with. That's what makes both
CRN574114 (skewed dash-dot plot around a squarer building) and CRN642050
(building occupying a fraction of a much bigger plot) come out right without
any plot-specific handling.

The one deliberate choice worth stating plainly: to go from "the walls" to
"the footprint", Stage 1 does a large morphological closing (dilate, then
erode, by the same radius) rather than a room-by-room flood fill. The radius
is sized from *this plan's own* room dimensions and door/window schedule
(never a constant), large enough to fill every room in solid and bridge every
scheduled opening. See [Known limitations](#known-limitations) for what that
trades away.

## The pipeline, stage by stage

Each stage is one file with one clearly-named entry point; every stage's
input and output are plain dataclasses defined once in `src/geometry_types.py`.

| Stage | File | Entry point | Input → Output |
|---|---|---|---|
| 0 — Extract | `src/stage0_extract.py` | `extract_page_data(pdf_path, crn)` | PDF path → `PageData` (wall polygons in feet, room labels, scale, opening widths, stated area) |
| 1 — Boundary | `src/stage1_boundary.py` | `compute_boundary(page_data)` | `PageData` → `BoundaryResult` (polygon in feet, area, match % vs. stated area) |
| 2 — Columns | `src/stage2_columns.py` | `compute_columns(page_data, boundary)` | `PageData` + `BoundaryResult` → `list[Column]` |
| 3 — Beams | `src/stage3_beams.py` | `compute_beams(columns, boundary, wall_union_ft)` | columns + boundary + wall geometry → `(list[Beam], isolated_column_ids)` |
| 4 — Render | `src/stage4_render.py` | `write_outputs(framing, output_dir)` | everything above → `layout.html` + `layout.json` |
| — | `src/pipeline.py` | `build_framing_result(pdf_path, crn)` / `run_for_crn(...)` | orchestrates 0→4, assembles assumptions/known-problems |

### Stage 0 — `src/stage0_extract.py`

- `extract_wall_shapes_pt` — pulls every filled, near-black polygon off the
  page (PDF points). This is the single fact the rest of the pipeline is
  built on: **walls are fills, everything else on the sheet is a stroke.**
- `extract_text_lines` / `parse_room_labels` — merges per-span text (PyMuPDF
  sometimes splits one label like `17' - 11" X 10' - 5"` mid-string) and
  regexes out room clear-dimension labels.
- `derive_scale_from_room_labels` — for each room label, ray-casts from its
  text position to the nearest wall material in all four directions, compares
  the measured clear span (in points) to the label (in feet). A sample is
  only trusted if the independently-measured X and Y scale agree within 15%
  — this automatically throws out rooms that are open on one side (no wall
  to hit), rather than silently returning a wrong scale for that axis.
- `derive_scale_from_wall_thickness` — fallback for plans where too few rooms
  are fully enclosed (CRN642050, whose rooms mostly open onto a central
  skylight void): measures the modal drawn thickness of every elongated wall
  fill and divides by the external-wall-thickness note parsed from the
  sheet's own text (`parse_wall_thickness_inches`, default 6" only if the
  note truly isn't there).
- `derive_scale` picks whichever of the two has enough evidence; **both are
  geometry/text-derived, never a typed-in constant.**

### Stage 1 — `src/stage1_boundary.py`

- `choose_closing_radius_ft` — half the largest room dimension or scheduled
  opening on *this* plan, clamped to [4, 15] ft.
- `close_wall_gaps` — dilate by that radius, erode back. Turns the raw wall
  network (thin, and often 6-8 disjoint islands before closing) into one
  solid mass whose outline is the footprint.
- `select_largest_shell` — largest connected piece, holes dropped (a
  fully-enclosed light well is still "inside" the structural envelope).
- `simplify_boundary` — tiny (0.05 ft) cleanup of buffering noise; deliberately
  too small to straighten a real skewed corner.
- `compute_boundary` ties these together and calls `area_match_percent`
  against the sheet's own area statement (`stated_area_sqft`, parsed in
  Stage 0 from the exact `"FIRST FLOOR LEVEL ... BUILT[- ]UP AREA ... SF"`
  text, balcony area added in when the sheet states it separately, as on
  CRN716485).

### Stage 2 — `src/stage2_columns.py`

Three independent rules, each ported almost directly from the assignment's
own starting logic:

- `boundary_corner_columns` — one per real corner (re-simplified at a coarser
  1.5 ft tolerance first, so a buffering-rounded arc from Stage 1 collapses
  back to the single corner it stands in for, instead of contributing several
  spurious columns along the curve).
- `wall_junction_columns` — one wherever two distinct wall polygons touch:
  covers both "internal meets external" and "internal meets internal", since
  both concentrate load the same way.
- `span_fill_columns` — evenly-spaced intermediates on any boundary edge
  longer than 15 ft.

`merge_nearby_columns` then collapses anything within 2 ft into one column
(corner-source wins the label on a tie), so a junction that lands right on a
corner doesn't get reported twice.

### Stage 3 — `src/stage3_beams.py`

- `perimeter_beams` walks the boundary ring in order and connects every
  column sitting on it — guarantees one closed loop around the whole
  perimeter regardless of how many corner/junction/span-fill columns ended
  up on a given edge.
- `interior_wall_beams` groups columns that share an X or a Y coordinate,
  connects only *adjacent* ones along that line (never skips over an
  in-between column), and only if the straight segment between them is at
  least 80% covered by wall material (`_wall_coverage_ratio` — measured as
  fraction of the line's *length* inside the wall union, not corridor area;
  an early area-based version could never reach threshold because a 4"-6"
  wall can't "fill" any reasonably-sized search corridor).
- `connect_isolated_columns` — a column can end up with zero beams if both
  neighbouring wall runs along its line are interrupted by a doorway (this
  happens once, on CRN574114). Rather than ship a floating column, it's
  wired to its nearest neighbour and reported back so Stage 4/README-style
  reporting can flag it as not wall-confirmed.

### Stage 4 — `src/stage4_render.py`

- `build_framing_svg` — plain-line SVG (black boundary, blue beams, dark-red
  column squares) at true relative proportions.
- `build_comparison_html` — that SVG next to a rasterized copy of the
  original PDF page, styled as a technical sheet (white background, black
  rules, one accent colour per element) rather than a dashboard.
- `build_output_json` — the JSON shape sketched in the assignment brief:
  `boundary`, `columns`, `beams`, `assumptions`, `known_problems`.

## Assumptions encoded in the code

(also written into every `layout.json`'s `"assumptions"` list at run time)

- Boundary = outer face of exterior walls, from filled wall polygons only.
- Door/window openings are bridged with a closing radius derived from this
  plan's own rooms and schedule, not a fixed constant.
- A balcony is part of the boundary whenever it's enclosed by wall material
  that survives closing; its area is added to the stated built-up area for
  the match check when the sheet lists it separately.
- Columns: every boundary corner, every wall-to-wall junction, plus
  intermediates on any straight run over 15 ft.
- Beams: only proposed where a wall actually runs between two aligned
  columns — never inferred across open space.

## Known limitations

Written here and in every run's `known_problems`, not swept under the rug:

- **The closing radius smooths real notches narrower than itself.** A sharp
  concave step in the true wall line that's narrower than twice the closing
  radius gets rounded into a gentle curve on the drawing (visible on all
  three outputs, most on CRN642050's rounded stair-void notch and
  CRN716485's balcony edge). The radius is picked to be big enough to swallow
  every room whole — the trade-off is real, and stated rather than hidden.
- **A void that's open on one side gets no beam on that side.** Stage 3 only
  proposes a beam where a wall is actually drawn; a stair void or passage
  that's genuinely open to its neighbour on one edge is left unsupported
  there in the output, rather than guessing a beam that isn't backed by
  anything on the sheet.
- **One column per run needed a distance-only fallback beam** (CRN574114,
  see `connect_isolated_columns`) because both wall runs on either side of it
  are broken by a doorway. Flagged in that run's `known_problems`, not
  silently presented as equivalent to a wall-confirmed beam.
- **CRN716485's structural hints were read but not consumed.** The plan
  annotates `CONCEALED BEAM` runs, `FC(8"X18")` column callouts and "column
  stops in ground floor roof" in text/colour. They were useful for visually
  cross-checking Stage 2's output (several `wall_junction` columns land
  right on the architect's own `FC` markers) but the pipeline doesn't parse
  or act on them — a same-floor plan gives no information about what the
  floor below looks like, so "does this column stack" isn't answerable from
  this input regardless.
- **No grid-snapping.** Columns aren't forced onto a regular A/B/C grid; two
  columns that an engineer would probably align to the same gridline can be
  a few inches apart in the output if the underlying walls are. The
  assignment explicitly doesn't require grid labels, so this was left as-is
  rather than adding a snapping heuristic that risks moving a column off the
  wall it's actually sitting on.

## With another week

- Grid-snap columns (cluster near-aligned rows/columns and pull outliers onto
  the shared line) so the beam network reads more consistently as rows and
  columns rather than following each wall's exact centroid.
- Detect fully-enclosed voids (stair/lift shafts) explicitly and force a beam
  loop around them even where one edge has no wall, instead of only ever
  beaming where wall material already exists.
- A smarter boundary step for notches narrower than the closing radius: run
  the closing at two radii (small, for gap-bridging only; large, for
  room-swallowing) and reconcile, instead of one radius doing both jobs.
- Parse and cross-validate against explicit architect hints (`CONCEALED
  BEAM`, `FC(...)` callouts) where present, as a second opinion on Stage 2/3
  rather than a replacement for the geometric derivation.

## Tests

`tests/` has both unit tests per stage (synthetic geometry, so they don't
depend on any one CRN's specifics) and an integration suite that runs the
real pipeline against all three `test-plans/` PDFs and checks structural
invariants — closed boundary, positive areas, every beam referencing a real
column, every column reachable by at least one beam, area within a sane band
of the stated figure, and that scale is always geometry/text-derived. 51
tests, all passing:

```bash
python3 -m pytest -v
```
